# Jump 性能检查 · 2026-10-20

> 后续已完成优化，见 [性能优化结果](performance-optimization-2026-10-20.md)。下文保留优化前的检查数据与结论。

当前配置下，常用命名操作响应较快，未发现持续高 CPU、崩溃或短时资源持续增长。明显慢点集中在方案编辑器；大数据量时，启动、方案菜单和方案管理页出现明显延迟。配置保存还存在阻塞界面线程的结构性问题。

本轮仅检查与记录，没有修改产品源码、重新打包或更新 dist。

## 环境与测量口径

- 本机 Windows 11，i5-13600KF，14 核／20 线程，32 GB 内存。
- 使用现有 Debug `/Od` 开发版；可执行文件 SHA-256：`0046fb92a2837274556f9c2df86515bff559e6106fe33b01b104fde58fa099ef`。这些数值不能直接代表 Release 性能。
- 仅使用项目自己的 Windows 保存对话框测试宿主和独立配置，原 `build/dev/settings.ini` 在测试退出时通过 SHA-256 校验未变。
- 当前配置：4 条已保存的方案／流程，0 个项目，27,442 字节。
- 压力配置：100 个自定义方案、100 个项目；每个方案 8 个字段，其中 5 个字段各 20 个候选；配置 2,534,094 字节。面板活动方案保持为内置资产文件。编辑器测试打开列表第一项，压力场景该项的字段／候选也更多，因此编辑器差值不能全部归因于方案数量。
- 耗时为发出操作到窗口／控件就绪并处理同步消息；多数动作还包含一次同步重绘。设置内嵌表单通过设置窗口统一重绘。候选点击使用真实鼠标，并读回原保存框文件名确认回填完成；其余多数按钮使用 Windows 控件消息。
- 不含 DWM 最终呈现、显示器延迟和系统菜单动画。2 ms 轮询及窗口枚举存在测量开销。
- 启动测量为 Windows 已有文件缓存时的 3 次进程启动，终点是控制窗口可响应；不是开机冷启动。
- 多数动作采样 3–5 次，候选／字段切换各 8 次，方案编辑器 24 次，规则页切换 15 次。助手首次附着仅各 1 次。小样本不能用于推断长期分位数或罕见卡顿频率。

## 资源占用与重复操作

- 后台空闲工作集：当前约 13.4 MiB，压力约 14.3 MiB。
- 助手显示时工作集：当前约 25.7 MiB，压力约 27.6 MiB。
- 设置页空闲工作集：当前约 32.3 MiB，压力约 34.4 MiB。
- 打开 Windows 文件选择框等窗口后，工作集升至约 69–71 MiB；随后重复操作趋于稳定。仅凭这一阶段增长不能认定泄漏。
- 当前配置连续 20 轮切换设置页并打开／关闭编辑器：工作集 69.18 → 69.35 MiB，私有提交 16.80 → 16.93 MiB，句柄 709 → 709，USER 对象 116 → 116，GDI 对象 100 → 98。
- 压力配置相同 20 轮：工作集 70.65 → 70.89 MiB，私有提交 19.84 → 18.57 MiB，句柄 708 → 697，USER 对象 116 → 114，GDI 对象 101 → 99。
- 空闲 CPU 采样为单核 0–0.76%，按 20 个逻辑处理器折算，整机约 0–0.04%；采样包含定期消息探测，未测到持续后台忙循环。多数空闲区间没有 I/O，助手刚出现后的 3 秒有少量初始化 I/O。
- 空闲控制窗口消息往返通常约 1–3 ms，各场景最大低于 7 ms。

短时采样没有发现资源持续增长，不能替代长时间运行验证。

## 需要优先处理的性能问题

### 1. 大配置启动和方案相关操作明显退化

**已测事实：** 进程启动由约 41 ms 增至 3.68 s；方案菜单由约 17 ms 增至 382 ms；命名方案页切换由约 24 ms 增至 401 ms。其他大部分页面、候选回填和名称输入保持较快，说明主要瓶颈集中在配置与方案管理路径。

**代码证据：** `src/model.cpp:352` 的 `load()` 在创建窗口之前同步执行，逐键调用 Windows profile API、读取并解析方案结构。`src/structured_naming.h:282` 的 `namingSchemeCatalog()` 每次遍历已保存方案并反序列化、校验、复制；`src/main.cpp:4810` 的选择逻辑和 `4885` 的列表构建会多次调用它，另有按方案 ID 再遍历解析的逻辑。

**建议：** 统一维护已解析的方案目录，按配置版本更新；列表、菜单、编辑器共用缓存与 ID 索引。单独拆分记录启动时配置读取、解码与目录初始化耗时，再决定是否改为一次读取配置。压力场景同时增加了方案、项目和候选，尚未对每一项成本做独立归因。

### 2. 同步保存配置可能阻塞界面

**已测事实：** 正式当前配置复测中，收起名称并记录历史最大 280 ms，较慢一次约 264 ms 在消息处理阶段，最后重绘仅约 16 ms。前置采样还出现约 0.97 s 和 2.10 s 的同一路径延迟，正式复测未稳定重现，不能把它们视为典型耗时。

**代码证据：** `src/structured_ui.h:2`、`257` 的最近名称记录／确认路径调用 `persist()`；`src/main.cpp:2535` 直接在调用线程执行 `save()`。`src/model.cpp:544` 的保存会序列化整个配置，写文件、`FlushFileBuffers`，首次保存前备份，再以 `MOVEFILE_WRITE_THROUGH` 替换文件；遇共享冲突还会等待重试。

**建议：** 最近名称等频繁变更可合并后交给单一后台写入队列；显式保存要有完成／失败反馈，退出时等待必要落盘，保留备份、原子替换和错误处理。不要简单删除可靠落盘步骤。尚未使用跟踪工具确认偶发长延迟具体花在序列化、备份、磁盘还是外部文件锁上。

### 3. 方案编辑器初始化和切页刷新偏重

**已测事实：** 当前配置打开编辑器中位约 468 ms，已足够让人感觉到等待；压力场景约 1.64 s。当前配置前几次打开的状态就绪等待约 459–478 ms，最后重绘约 20–24 ms，主要时间在窗口完成初始化之前。

**代码证据：** `src/naming_designer.h:275` 起的初始化一次性创建简单视图和隐藏高级页的大量控件；`255` 的 `designerLoad()` 在页切换时执行完整布局、简单视图填充和字段填充。`608` 还会重新构建整个方案目录并复制模板。

**建议：** 打开时先准备当前页，隐藏页按需初始化；切页仅更新发生变化的内容，批量布局与绘制。缓存方案目录与编辑器局部刷新要一起处理。需要插桩进一步区分控件创建、候选填充和布局的占比，现有数据不能证明某一处占了全部耗时。

### 4. 次要改进与未复现风险

- 前后缀、替换展开收起约 0.15–0.18 s，可减少整个面板重建，优先级低于上述三项。
- `src/model.cpp:260` 的自定义正则匹配／替换仍在界面调用链中执行，代码已有长度限制和复杂度错误处理。本轮未对复杂正则做专项压力测试，只作为后续排查点。
- 目录扫描、编号计算已有后台任务与取消机制；本轮未对大目录、网络盘或离线盘单独施压，不对这些环境下的最坏延迟下结论。
